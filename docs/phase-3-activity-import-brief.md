# P3：个人活动 Markdown 导入任务书

- 任务阶段：需求与方案准备
- 总控版本：`2026-09-18T15:02:44+08:00`
- 前置状态：P1 数据底座、P2-A 财务 Agent 与 P2-TIME 已验收完成
- 目标用户：希望先用易编辑的 Markdown 逐步建立个人活动与消费参考资料的单用户

## 目标

建立第一条“Markdown 文本 → 结构化候选 → 用户确认 → 活动模板入库”纵向链路。Markdown 是输入数据，不是系统指令；预览阶段不能产生业务写入，提交阶段必须幂等、可追溯且原子化。

本阶段结束后，用户应能提交一份虚拟活动 Markdown，看到系统识别出的新增、修改、冲突和待确认项，选择接受的变更并一次提交。重复提交同一导入请求不得重复创建模板。

## 用户流程

```text
输入 Markdown 文本
  → 限制大小并计算内容摘要
  → 提取活动候选与来源位置
  → Pydantic/业务规则校验
  → 返回 create / revise / conflict / unresolved 预览
  → 用户明确选择
  → 原子提交到活动模板及其修订
  → 返回可纠错的导入结果
```

## 必须满足的行为

1. 预览不创建模板、活动发生记录、账目、预算或收入记录。
2. Markdown 中的提示词、代码块、链接和 HTML 不能改变 Agent 权限、工具、系统规则或触发代码执行。
3. 每个候选保留稳定候选 ID、来源标题/行号、原文摘要、规范化字段、校验问题和建议动作。
4. 精确同名与现有模板的关系必须显式展示；文字相似不得静默合并。
5. 参考金额只用于预测，不产生已支付账目。金额范围不能未经规则擅自压成单一事实。
6. 同一导入请求同一载荷重放原结果；同一请求标识不同载荷稳定冲突。
7. 提交前重新校验模板版本；并发变化不能被静默覆盖。
8. 一批已选择变更要么全部提交，要么全部回滚；失败后不得留下半批模板或幂等回执。
9. 只保存必要的结构化事实和安全摘要；原始个人 Markdown 的持久化范围必须由方案明确说明。
10. SQLite 提供快速开发证据，涉及并发、锁和唯一性时以 PostgreSQL 为目标验收环境。

## 首个切片的输入示例

```markdown
# 我的活动

## 食堂午餐
- 通常每次 15–20 元，只用于预测。
- 上课日一般一次；休息日不一定。

## 健身房
- 周末可能去零次、一次或两次。
- 交通费单独记录。
```

示例完全虚构。技术方案必须说明标题层级、允许的字段、自由文本、金额范围、未知字段和重复标题分别怎样处理。

## 已有基础

- `activity_template` 与不可变 `activity_template_revision` 已存在。
- `FinanceService` 已提供创建和修订活动模板的幂等业务命令。
- `activity_occurrence` 与账目分配已存在，但导入预览不得创建它们。
- FastAPI、Pydantic、SQLAlchemy、Alembic、SQLite/PostgreSQL 测试基础已经建立。
- 当前模型只有单一 `reference_minor`，还没有活动组合表或导入批次表。

## 需要方案明确的事项

1. 使用严格 Markdown 语法、Markdown AST 库还是模型结构化提取；首版是否联网。
2. 预览状态采用持久导入批次，还是无状态摘要加重新解析。
3. 是否在本阶段新增活动组合/成员表，还是先只导入模板并保留组合候选。
4. 参考金额范围怎样保存；是否扩展模板修订模型，还是首版只接受精确参考金额。
5. 原始 Markdown 是否保存、保存多久，以及来源行和内容摘要如何追溯。
6. API 路径、请求/响应 DTO、严格字段、错误码、大小限制和提交确认方式。
7. 批量提交如何复用现有 `FinanceService`，同时保证整批事务与幂等。

这些事项由 P3-D7 给出建议，P3-C8 提供风险和验收矩阵，再由总控冻结 `P3-IF-001`。冻结前不得开始产品实现。

## 本阶段暂不包含

- React/Electron 页面和真实文件选择器；先验证文本 API 与业务链路。
- DeepSeek 联网解析、网络搜索、RAG、个人记忆或理财教学。
- 自动生成活动发生、账目、预算或提醒。
- 模糊相似活动的自动合并。
- OpenClaw/微信运行时恢复和真实个人活动数据导入。
